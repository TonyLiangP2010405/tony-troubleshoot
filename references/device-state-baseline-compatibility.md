# 基线、设备持久化状态与 API 版本兼容规则

本规则用于参数层长时间无差异、客户操作记忆不完整、设备状态疑似隐藏在公开参数之外，或设备固件与现有 API 文档只有小版本差异的情况。

## 基线制度

为每份快照记录设备稳定 ID、型号、固件/API 配置、采集时间和时区、命令/字段范围、来源、哈希和可靠性：

- `known_good`：有证据证明系统当时正常的快照。
- `pre_fault`：采集时间早于故障，但不一定证明当时每项功能正常。
- `session_start`：本次排障首次设备动作前的只读快照，只能对比本次会话后续变化。
- `post_action`：重启、换线、改配置或复位等获批动作之后的快照。
- `resolved`：客户确认恢复时的验证快照。

比较前核对型号、硬件代次、固件/API 配置和采集范围。规范化时间、计数器、运行时长、动态地址、会话 ID 等易变字段；不要把预期变化误判为配置差异。可靠基线不存在时必须写“无法判断故障前是否被改动”，不能用 `session_start` 填补历史事实。

## 客户记忆不可靠或参数层零差异

客户说法仍是线索，但不是基线。不要围绕记不清的每次点击无限逆推，改为：

1. 取得并验证任何真实的故障前/已知正常快照；没有则建立 `session_start`。
2. 对同型号正常设备、受影响设备和可靠基线做标准化字段比较，保存零差异及差异证据。
3. 用换端、换链路或对照设备判断症状是否随设备迁移；排除电源、线缆、网络、信号源和显示端等外部因素。
4. 分开测试易失运行态和持久化状态，不把“参数看起来相同”写成设备内部必然相同。

## 重启与工厂复位的判别含义

- `reboot` 重新建立进程、服务和易失运行态，通常不清除持久化配置。无论 API 如何命名，它都会中断业务并改变现场，执行前需准确文档和对该设备的明确授权。
- `restorefactory`/factory reset 会删除或重建持久化配置，可能改变地址、认证、路由、配对和管理可达性。它既是恢复动作也是高影响判别动作，不是参数层查不出问题后的自动下一步。

只有同时满足以下条件才可向用户提出工厂复位：

1. 症状稳定绑定目标设备，外部链路和可见参数已有支持与反证。
2. 软重启已获批执行且无效，或准确官方文档说明该情形不适合先重启。
3. 已导出并验证恢复所需的配置、许可、地址、配对、路由和凭据恢复方案；可疑旧备份不会自动回灌。
4. 已说明停机范围、失联风险、恢复步骤、验证条件和回退限制。
5. 用户对准确设备和 `restorefactory` 动作单独明确授权。

复位后先用最小干净配置验证。如果恢复正常，只能先写“持久化配置或内部状态相关”。若需回灌旧配置验证复现，必须再次说明风险并另行授权。只有重复性和机制证据足够时才能进一步写成配置区损坏；否则保留隐藏配置、缓存或状态组合等替代解释。

## 小版本 API 兼容性探测

先尝试用官网产品页、发行说明或 API 文档声明建立适用性。只有以下条件全部满足时，才能在没有明确声明的情况下做有界经验探测：

- 准确型号、产品代次、传输和认证方式相同；
- API 主版本相同，差异仅为固件/API 小版本；
- 选择的 2–3 条命令在现有文档中明确只读、低成本、无危险参数，优先身份、版本、能力和总体状态；
- 按原安全规则保存请求、响应、时间和文档位置。

出现未知响应、字段语义变化、连接异常、速率异常或任何可能改变状态的迹象立即停止。成功只将已测试命令标为 `empirically_compatible`；其它命令仍为未验证。主版本、型号、认证、传输或写入语义不一致时不得探测，继续登记文档阻塞。

## 各模式字段检查

- `triage`：所有核心响应保存原文并做必要字段检查；只对深入设备、异常/畸形响应和诊断命令做完整字段审计。
- `deep`：完整审计问题域内实际用于支持或反驳结论的字段。
- `audit`：对全部适用设备、命令、参数、分页和字段执行完整覆盖审计。

轻量检查必须记录解析是否成功、必要字段是否存在及证据路径；不得把它统计为完整字段覆盖。
