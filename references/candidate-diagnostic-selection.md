# 候选问题多选规则

本规则位于资料审阅和初始分类之后、正式设备诊断之前。它让客户决定优先顺序，同时保持证据纪律：客户选择不是根因证明，未选择也不是排除证据。

## 生成完整但有限的候选集

汇总用户描述与操作、所有当前已收到文件的审阅结果、本地 IPAV/ODM 与官网资料、命令来源、Web UI 被动证据、拓扑和可用基线。列出所有满足以下条件的候选：

- 能解释至少一个主要症状，并有现场事实、适用资料或明确缺口作为依据；
- 尚未被证据排除；
- 与其它候选具有不同的可验证机制或首个判别动作。

合并同义候选，不为了显得全面罗列与型号、拓扑或症状无关的理论故障。已经排除的解释放在“已排除，不可选择”区并附证据，不混入复选项。高影响资料仍未收到时可先展示 `provisional` 候选，并明确新资料可能改变列表。

候选编号在同一 session 内必须稳定：某个 `H-xxx` 一旦向用户展示，就不得改名、换义或分配给另一个候选。后续新增候选使用新的编号；合并或排除旧候选时保留原编号并记录去向。

## 多选展示格式

按以下字段展示每个候选：

```markdown
请选择希望优先排查的项目，可多选。建议优先：H-001、H-003。

- [ ] H-001 — <可能问题>
  - 分类/维度：<category / dimension>
  - 为什么可能：<支持证据>
  - 反证或缺口：<反证/未知>
  - 当前可能性：<high|medium|low，不是最终结论>
  - 第一步：<最小只读或用户观察动作>
  - 成本/影响：<时间、停机、物理操作>
  - 写操作：<none 或 later separate approval>

回复示例：`H-001,H-003`。也可以回复 `全部排查` 或 `你来决定顺序`。
```

客户端确实支持多选控件时可以使用，但控件必须允许一次选择多个候选并保留稳定编号；不要用互斥单选问题代替。

## 记录和执行

在展示前，把所有可选候选的 `customer_visible=yes`，checkpoint 设为 `pending_user`。与多选有关的固定账本列为 `customer_visible`、`customer_selected`、`customer_priority`、`customer_selection_note`、`selection_updated_at`；不得为同一含义临时另造字段。收到回复后：

- 明确多选：所选行写 `customer_selected=yes` 和 `customer_priority`，其余可见行写 `customer_selected=no`；checkpoint 设为 `selected`。
- `全部排查`：所有可见候选写 `yes`，按 agent 的安全/信息增益排名生成客户优先级。
- `你来决定顺序`：记录客户原话，checkpoint 设为 `customer_deferred`；agent 按信息增益高、风险低、成本低和依赖关系排序。
- 暂不选择：保持 `pending_user`，不生成执行行，不发送设备诊断命令。

用户选择决定先后，不改变假设状态。只有后续证据才能把候选改为 `weakened|rejected|confirmed`。如果为安全或依赖关系需要调整所选顺序，先说明原因；不要悄悄改序。

新增候选或排序发生实质变化时，展示一份增量列表：新增、置信度变化、已排除及建议调整。允许用户追加、取消或重排；没有实质变化时不要重复询问。

多选只授权排查优先级。任何改变状态的命令、页面按钮、物理动作或停机测试继续遵守原有的单独授权和影响说明规则。
